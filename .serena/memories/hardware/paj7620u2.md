# hardware/paj7620u2

Datasheet-derived facts that shape the driver and the hardware design
(`docs/PAJ7620U2_DS.pdf`, V0.8).

- **I2C**: 7-bit slave address `0x73`, up to **400 kHz**, open-drain SDA/SCL
  with external pull-ups, no clock stretching, no general-call/address change.
- **Power**: VDD/VBUS 2.8…3.6 V; VLED 3.0…4.2 V. Operating current 2.8 mA
  typical *including* LED peaks.
- **IR LED**: pulse current **720…860 mA**, pulse width < 500 µs, duty < 5 %.
  The VLED rail, its decoupling and layout must survive that — thin modules
  drop fast gestures. A separate rail with local decoupling is mandatory in
  an industrial design; LED and logic ground tied.
- **INT**: open-drain, active-low, driven while a mask-enabled gesture is
  pending; cleared by reading 0x43/0x44.
- **Timing**: T1 > 700 µs after power-on, T2 > 400 µs after the I2C wake-up
  command; the sensor does not ACK before it is ready.
- **Modes are exclusive**: gesture engine (120 Hz normal / 240 Hz gaming) vs
  proximity (10 Hz, hysteresis window). The PS registers (0x69…0x6C) are only
  updated in proximity mode, so `paj_readProximity()` legitimately returns 0 in
  gesture mode. `paj_setProximityMode()` / `paj_setGestureMode()` (official
  sequences) do the switch; `PAJ_ENABLE_PS_MODE=0` removes them.
- **State machine** (register 0x45): 0 = Operation, 1 = Standby 1, 2 = Standby 2;
  S1/S2 degrade the detection rate, timing set by the 0x67…0x6E step pairs.
- **Gesture envelope**: 5…15 cm from the sensor centre, ±60° detection angle,
  60…600 °/s normal mode, ambient-light immunity < 100 kLux.
- Sensor orientation matters: rotating the module requires remapping the
  direction flags — `PAJ_GESTURE_ROTATE` does it in software.
- No host-accessible pixel array or FIFO in this map: nothing to stream, the
  host only reads results.

## Spontaneous MCU resets (bring-up checks)

A repeated `PAJ7620U2 gesture driver init...` banner on UART means the MCU
restarted; it is *not* a driver re-init (that path prints
`SENSOR HANG ... re-init`). Ranked causes:

1. **POR / brown-out** — the IR LED pulses 720…860 mA, and the sensor scans
   continuously while a hand is in view. Feeding VLED (or the whole module)
   from the WCH-Link 3.3 V pin (~100 mA) or through long/thin wires sags VDD
   below the MCU threshold. Fix on the hardware side: separate 3.3 V rail for
   the MCU + LDO with bulk capacitance (≥100 µF) and 10 µF/100 nF at the
   sensor, short ground return, LED ground tied to logic ground.
2. **PIN (NRST)** — reset button, WCH-Link, or an auto-reset USB-UART whose
   DTR/RTS toggles when the monitor re-opens the port.
3. **SW** — debugger flashing.
4. **IWDG/WWDG** — not enabled by this driver or the example.

Not causes: HardFault (the example's `HardFault_Handler` is an endless loop, so
the firmware would hang, not reboot), watchdog (never started), driver stack
usage (measured with `-fstack-usage`: largest frame 48 B in `paj_exti_init`,
driver frames ≤20 B, `main` 36 B against a 256 B linker stack).

The example prints the RCC reset flags at boot (`Reset: PIN POR ...`) and clears
them (`RCC_ClearFlag()`), then re-reads POR as a self-check and prints
`(RCC reset flags not cleared)` if RMVF did not take — that line invalidates the
whole flag report, so trust a scope over the flags in that case.
`PAJ_EXAMPLE_RESET_INFO=0` removes ~276 B of reporting.

A **reset loop** (banner every ~0.3 s, the `ready` line cut mid-word) is a supply
problem until proven otherwise: the sensor scans continuously from `paj_init()`
on and the LED pulses 720…860 mA. Decisive experiment: `pio run -e power_test
-t upload` (or `-DPAJ_EXAMPLE_POWER_TEST=1`) — the example calls `paj_shutdown()`
right after init (suspend ≈15 µA, no I2C) and prints `alive N` every 500 ms.
Rebooting stops → sensor supply/LED current; keeps rebooting → MCU rail, NRST or
the WCH-Link.
Equivalent no-code test: unplug VDD/VLED of the module and expect
`ERROR: PAJ7620U2 not responding!` plus a live board. `POR` on *every* boot is a
genuine power event each time (flags are cleared at boot, and the
`(RCC reset flags not cleared)` self-check stays silent), and `POR SW` means the
debugger re-attached after the dip. A burst of resets every ~30 ms after ~20 s of
continuous gestures points at a rail/LDO that collapses under sustained LED load
and recovers when the MCU drops the sensor. A bare module powered from 5 V
(VDD > 3.6 V, VLED > 4.2 V) produces exactly this loop.

**Confirmed (bench, 2026-10):** with the module fed from the WCH-Link 3.3 V pin
(~100 mA) the firmware POR-looped after ~20 s of continuous gestures; the same
board with `pio run -e power_test` (sensor suspended) reported `alive` > 250
(two minutes) with zero resets. Conclusion: the MCU/NRST/link are fine, the
3.3 V link rail cannot supply the IR LED — only separate VDD/VLED power fixes it.
There is no driver knob for LED current.
